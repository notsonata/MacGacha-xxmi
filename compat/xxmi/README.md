# HSR XXMI compatibility package

This directory owns the HSR-only XXMI compatibility inputs: the C hook runner,
focused SRMI patches, source pins, notices, the explicit build plan and the
offline package recipe. The app consumes the generated package under
`App/Resources/XXMI/`; no game, Wine runtime or installed state is modified by
these tools. The ignored `App/Resources/XXMI/` directory is generated output:
no DLL, EXE, ZIP or package binary is committed, and `docs/`, `.build/` and
release output stay out of Git.

## Released state

The current app release is `v0.3.0-xxmi.1`:
<https://github.com/notsonata/MacGacha-xxmi/releases/tag/v0.3.0-xxmi.1>

It is a regular, non-prerelease GitHub release. It is based on MacGacha 0.3.0

The standalone ZIP is a wrapper around the verified pair. Its layout is:

```text
XXMI-HSR-2.4.3-macgacha.3/

  hsr-srmi.zip
```

Extract the ZIP and choose the extracted `XXMI-HSR-2.4.3-macgacha.3` folder in
**XXMI → Import Package…**. The app reads `manifest.json` and `hsr-srmi.zip`
from that folder and ignores the wrapper's `README.txt`, `NOTICE.md` and
`licenses/`. The wrapper itself is assembled outside these source tools;
`scripts/xxmi-package.py` only produces the inner `manifest.json` plus
`hsr-srmi.zip` pair.

The raw `manifest.json` and `hsr-srmi.zip`, the GPL corresponding-source
archive and its checksum sidecar live on the separate compatibility release
`xxmi-2.4.3-macgacha.3`:
<https://github.com/notsonata/MacGacha-xxmi/releases/tag/xxmi-2.4.3-macgacha.3>

Injection is off by default and applies only to Honkai: Star Rail Global on the
exact `d3dmetal-wine11.20-gptk4.0b3` runtime bundle. The XXMI Launcher UI is not
included or opened. The user may relocate the mod library, and every launch
retains an immutable snapshot of the enabled mods and package. App updates are
disabled in this fork, no update signing key is provisioned, and users update
by downloading a new DMG from the releases page.

### Overlay resources (release blocker fixed)

`DirectX11/Overlay.cpp` loads three embedded DirectXTK SPRITEFONT resources
(`IDR_COURIERBOLD`, `IDR_ARIAL`, `IDR_COURIERSMALL`) with `FindResource`.
The earlier `cb60edd4…` build (and the released v1.2.2 `79da3363…`) linked no
resource object, so their PE resource directory is empty, `LockResource`
returns NULL and the DirectXTK `SpriteFont` constructor throws: the Overlay
cannot be constructed. The clean-tree rule omits the `.spritefont` suffix, so
the fonts never reached the build.

Relative to v1.5.0 exactly four files change: `Core/ZZMI/main.ini` (version),
`Core/ZZMI/Libraries/HP bar/characters.ini`, `Core/ZZMI/Libraries/HP bar/hp.ini`
and `Core/ZZMI/Libraries/SlotFix/SlotFix.ini`. `d3dx.ini` and the shader are
unchanged, so the normalized `d3dx.ini` pin is unchanged.

The shared XXMI DLL source is configuration driven, not an SRMI-only payload;
its README describes it as the XXMI Launcher core and documents ZZMI's SlotFix
usage. ZZMI 1.5.2 uses pool variables and `$Poolt[*]` full-range assignment,
which the upstream XXMI Libraries `v1.2.0` release notes introduce. The builder
therefore requires an explicit `coreCompatibility` record, pins the shared core
at `v1.2.3`, and fails closed when the declared minimum is newer than the
pinned core. ZZMI does not publish a formal library-version range, so the floor
is derived from the upstream XXMI Libraries release notes for the INI features
the pinned ZZMI source actually uses. This is a feature-level compatibility
check, not a runtime or rendering guarantee.

The generic core corrections (patches 0001–0007 and 0009–0011) are part of the
shared DLL. Patch 0008 is an SRMI `TextPrinter.hlsl` change and is **not**
applied to ZZMI; the unmodified ZZMI shader is pinned and packaged.

The ZZMI package remains a local candidate. It is not part of the current
release, not committed, and not bundled by an app release. The app integration
and live rendering/injection testing are still pending. The target-aware runner
source is `compat/xxmi/runner/xxmi_hook_launcher.c`.
The historical HSR source remains unchanged in `srmi_hook_launcher.c`, so the
released HSR runner and its source pin are preserved. The runner contract is:

```text
hook-runner.exe --loader <injector> --payload <payload>
  [--target-exe <StarRail.exe|ZenlessZoneZero.exe>]
  -- <resolved game command...>
```

`--target-exe` defaults to `StarRail.exe` for backward compatibility. Only the
two names above are accepted; unknown, missing or duplicate values fail before
the loader is opened. The chosen name drives the game-path suffix check, the
already-running preflight, `WaitForInjection`, exact image/module verification
and the visible-window wait. The app must pass `--target-exe
ZenlessZoneZero.exe` for ZZZ. It should pass no flag to the released HSR package
runner; a future HSR runner rebuilt from the generalized source accepts the
same default.

After `--`, the runner binds the launch executable and target to the exact
commands MacGacha resolves: the game image first, a Proton `steam.exe` shim or
`jadeite.exe` immediately followed by the game image, or no other shape. It
never scans later arguments for a target-looking path. An arbitrary leading
executable with a trailing target name, or an approved wrapper whose second
argument is not the selected game image, fails before `3dmloader.dll` is
loaded. Trailing Unity and display arguments remain unchanged.

Build the ZZZ package from authenticated inputs:

```sh
scripts/xxmi-build-runner.sh \
  --source compat/xxmi/runner/xxmi_hook_launcher.c \
  --runtime-root "$MACGACHA_WINE_RUNTIME_ROOT" \
  --clang /usr/bin/clang \
  --lld-link "$LLD_LINK" \
  --sdk-root "$(xcrun --sdk macosx --show-sdk-path)" \
  --lld-library-path "$LLVM_LIB_DIR" \
  --output "$OUTPUT_DIR/hook-runner.exe"

python3 -I scripts/xxmi-package.py build \
  --runner "$OUTPUT_DIR/hook-runner.exe" \
  --injector "$XXMI_LIBS_EXTRACT/3dmloader.dll" \
  --payload-dir "$ZZMI_PAYLOAD_DIR" \
  --output-dir App/Resources/XXMI \
  --pins compat/xxmi/zzz-source-pins.json

python3 -I scripts/xxmi-package.py verify \
  --directory App/Resources/XXMI \
  --pins compat/xxmi/zzz-source-pins.json
```

`$ZZMI_PAYLOAD_DIR` is the tagged ZZMI `ZZMI/` tree (`Core/`, `ShaderFixes/`
and `d3dx.ini`) plus the shared core `d3d11.dll` and `d3dcompiler_47.dll`.
`Mods/`, `ShaderCache/`, `d3dx_user.ini` and logs remain rejected. The builder
verifies the pinned source version, config files, core compatibility, feature
use, shader, injector, payload and compiler. `zzz-source-pins.json` also
contains a complete 47-file runtime size/SHA-256 mapping and the exact
normalized `d3dx.ini` size/SHA-256, derived from the pinned source tree. Build
and verify reject any missing, additional or altered runtime file even when a
tampered package regenerates its own manifest and archive hashes, and they
compare manifest provenance to the pins. It rewrites `[Loader] loader` to
`hook-runner.exe`, comments any active `launch` path, inserts a neutral
`proxy_d3d11 =` when the upstream configuration omits it, and disables logging
through either `calls`/`debug` or `log_level`.

The runner pin is an exact locally compiled artifact:
`SHA-256 98c202f777848bb4811aac1bd86703db89e1a78fbfcd40653f4ffbcfcc730172`,
size 12800, built from source SHA-256
`59b19974eeb8b9ce5801bc94b7cf9b2350ea8ffbfaf10180fb8380be069f71a5`.
The builder requires both the exact hash and size; a source pin alone, a
string-marker-only PE, or a hash/size mismatch is rejected. A different
toolchain can produce a different runner, so replacing this pin requires a new
local build plus the same package and provenance review.

`App/Resources/XXMI/` is generated output under the already ignored path and
matches the app's flat `XXMI` bundle resources. The ZZZ manifest uses the
unique sidecar name `zzz-zzmi.manifest.json`, so it can sit beside the HSR
`manifest.json` and `hsr-srmi.zip` even after Xcode flattens the resource
directory. Package builds update only their own manifest and archive files,
preserve unrelated entries, and refuse to replace a different package's own
manifest. These tools never write ZZZ `GENERAL_DATA.bin`, game settings or an
installed prefix.

[Overlay resources](#overlay-resources-release-blocker-fixed)). Patch 8 produces the numeric shader used by the live
baseline. The build plan records the expected clean and patched tree hashes,
object hashes and final candidate hashes. (For the released v1.2.2 package the
stage candidates were `c563d40c…`, `52bac2fe…` and `79da3363…`.)

The clean tree is derived from the upstream archive by a fixed rule: every
file whose lower-case suffix is `.asm`, `.bat`, `.c`, `.cpp`, `.def`,
`.filters`, `.h`, `.hpp`, `.ini`, `.md`, `.ps1`, `.rc`, `.sh`, `.sln`, `.txt`,
`.vcxproj` or `.yml`, plus an empty `version.generated.h` (which upstream's
release workflow generates and `version.h` includes). The same rule reproduces
the v1.2.2 pin `77862e4e…` exactly.

## Rebuild dependencies

The source build is deliberately not self-fetching. Provide every input by
path; the tools fail with a complete missing-input report instead of falling
back to a prebuilt DLL:

- macOS 27 and Apple Clang (`clang++`) for the `x86_64-pc-windows-msvc` target.
- The Clang resource include directory (for example the Xcode toolchain's
  `usr/lib/clang/<version>/include`).
- `lld-link` (the Rust toolchain's bundled copy is sufficient) and, when its
  sibling `libLLVM.dylib` is not discoverable, `--lld-library-path`.
- MSVC 14.44.35207 headers and libraries, and Windows SDK 10.0.26100.7705
  (include directory `10.0.26100.0`) headers and x64 import libraries, from
  the official packages recorded in the plan's `provenance.toolchain`.
- The clean pinned XXMI Libraries source tree.
- The authenticated third-party object tree used by the verified build
  (`DirectXTK`, `NktHookLib`, PCRE2, the MASM helper). These objects are
  hash-checked, not rebuilt by these tools. For the v1.2.3 plan they are the
  2026-11-04 source rebuild with the NktHookLib relocatable-code correction;
  their source-correspondence archives are pinned in the plan's `provenance`
  record and required by `xxmi-source-release.py`.
- `DirectXTK/Inc/SimpleMath.inl`, which the clean archive omits.
- The three `*.spritefont` Overlay fonts from the pinned upstream archive, at
  the root of the `--generated-assets` directory (the clean-tree rule omits
  the suffix). The plan pins their SHA-256, size and git blob SHA-1;
  `scripts/xxmi-payload-resources.py describe --source CLEAN
  --generated-assets DIR --upstream-archive XXMI-Libs-Package-065dc746.tar.gz`
  re-authenticates them against the archive digest and prints the plan record.

The checked-in `build/payload-build-plan.json` contains only tokenized paths and
recorded hashes. It never contains a temporary build root, a developer home
directory, or a developer-specific checkout path. The plan records the expected
object and candidate hashes, so a different compiler or SDK version fails closed
instead of silently producing an unverified DLL.

These tools are explicit-input and source-only. They do not clean-room rebuild
the authenticated third-party objects, and the shader patch is applied
separately from the DLL build. A successful run validates the pinned input set
and requires the recorded candidate hash. It is not a claim that any toolchain
alone reproduces the released DLL byte for byte.

## Commands

### Runner

```sh
scripts/xxmi-build-runner.sh \
  --source compat/xxmi/runner/srmi_hook_launcher.c \
  --runtime-root "$MACGACHA_WINE_RUNTIME_ROOT" \
  --clang /usr/bin/clang \
  --lld-link "$LLD_LINK" \
  --sdk-root "$(xcrun --sdk macosx --show-sdk-path)" \
  --output "$OUTPUT_DIR/hook-runner.exe"
```

Add `--lld-library-path DIR` when `lld-link` needs its sibling LLVM library.
`--expected-sha256` makes a rebuild fail unless it matches a pinned artifact.
Use `--source compat/xxmi/runner/xxmi_hook_launcher.c` for the target-aware
runner; the command above remains the historical HSR runner source. The build
script verifies the PE output and prints its SHA-256, but does not assume a
byte-identical rebuild.

### Payload DLL

Validate all source, patch, SDK and object inputs without compiling:

```sh
scripts/xxmi-rebuild-payload.py --check \
  --source "$XXMI_LIBS_SOURCE" \
  --generated-assets "$REFERENCE_SOURCE" \
  --third-party-objects "$REFERENCE_OBJECTS" \
  --clangxx /usr/bin/clang++ \
  --clang-resource "$CLANG_RESOURCE_INCLUDE" \
  --msvc-include "$MSVC_INCLUDE" \
  --msvc-lib "$MSVC_LIB" \
  --windows-sdk-include "$WINDOWS_SDK_INCLUDE" \
  --windows-sdk-lib "$WINDOWS_SDK_LIB" \
  --lld-link "$LLD_LINK" \
  --lld-library-path "$LLVM_LIB_DIR"
```

Use the same arguments with `--output-dir "$OUTPUT"` to build stage 1 (base
`1f016674…`) and stage 2 (`81399ea2…`) and stage 3 (final `e519f024…`). The command verifies the clean source
tree, every patch, every compiled object, every stage's `DirectX11.res`, the
linked resources and all three linked candidates. It does not run Wine or the
game. `scripts/xxmi-payload-resources.py verify d3d11.dll` checks a built DLL's
resources on its own and rejects a resource-less one.

### Shader

From the repository root, applying into the payload root (the directory
containing `Core/` and `d3dx.ini`):

```sh
patch -d "$SRMI_PAYLOAD_DIR" -p1 --fuzz=0 \
  -i "$REPO_ROOT/compat/xxmi/patches/0008-srmi-text-printer-vkd3d-all-literals.patch"
```

The packaged shader must hash to `c5071500…`; the package builder rejects a
different baseline.

### Package and verification

```sh
python3 -I scripts/xxmi-package.py build \
  --runner "$OUTPUT_DIR/hook-runner.exe" \
  --injector "$XXMI_LIBS_EXTRACT/3dmloader.dll" \
  --payload-dir "$SRMI_PAYLOAD_DIR" \
  --output-dir App/Resources/XXMI \
  --pins compat/xxmi/source-pins.json

python3 -I scripts/xxmi-package.py verify \
  --directory App/Resources/XXMI \
  --pins compat/xxmi/source-pins.json
```

The payload directory may be a working PoC payload that also contains `Mods/`,
`ShaderFixes/`, `ShaderCache/`, `d3dx_user.ini` and logs. Those entries are
ignored and never packaged. Any other unexpected root file is an error, so a
personal file cannot become part of the package by accident. Symlinks, traversal
paths and case-insensitive duplicate paths are rejected.

Run the focused host tests:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 -I scripts/tests/test_xxmi_package.py -v
```

`scripts/test.sh` and the CI workflow also run
`python3 -I -m unittest discover -s scripts/tests -p 'test_xxmi_*.py' -v`, so
the package and source-release tools are covered without a manual step.

## Generated artifact contract

`App/Resources/XXMI/manifest.json` (schema version 1) has:

- `schemaVersion`, `id` (`hsr-srmi`), `version`, `gameID` (`starrail`);
- `supportedRuntimeBundleIDs` (`d3dmetal-wine11.20-gptk4.0b3` only);
- `runnerPath` (`hook-runner.exe`), `injectorPath` (`3dmloader.dll`) and
  `payloadPath` (`payload/d3d11.dll`), all relative;
- `archiveSize` (Int64) and `archiveSHA256`;
- `files` (path, size, sha256 for every archive member);
- `sources` (pinned source provenance) and `license` (`GPL-3.0-only`).

`hsr-srmi.zip` contains exactly the declared regular files, no directory
entries, no symlinks and no manifest. Entries are sorted, use DEFLATE, fixed
1980-01-01 timestamps, Unix creator system and mode `0644`. The manifest is an
external sidecar and never describes or contains itself. Versioned manifests
let the app import an independently updated XXMI package without an app update.
The released standalone ZIP wraps this pair in a `XXMI-HSR-<version>/` folder
with `README.txt`, `NOTICE.md` and `licenses/`. Those wrapper files are outside
the verified pair and are not covered by the manifest hashes.

The bundled `d3dx.ini` is normalized: `[Loader]` targets the pins-selected game
executable (`StarRail.exe` for HSR, `ZenlessZoneZero.exe` for ZZMI),
`hook-runner.exe` and `d3d11.dll`; `[System] proxy_d3d11 =` is empty so the app
can substitute the actual selected runtime backend at install/snapshot time;
active launch paths are commented and PoC API logging is off; developer
absolute paths are rejected.

## Core runtime corrections

Compatibility package `2.4.3-macgacha.3` keeps 0009 and 0010 and adds
`0011-srmi-conditional-fold-fail-closed.patch` for XXMI Libraries v1.2.3.
v1.2.3 folds an `if`/`elif`/`else` chain whose branches each drive one fixed
shader-resource slot into a `ConditionalSlotCopyOperation` inside a bind/fetch
batch. `collect_conditional_chain` reads, and the folded operation later
evaluates, the chain's expression without knowing about 0010's
`expression_valid`. In the real optimiser order (`optimise`, then noop removal,
then `merge_shader_resource_batches`) 0010 already removes an invalid node
before batching. 0011 makes the fold itself refuse an invalid head or nested
`elif`, so an invalid branch can never be batched or its partial expression
evaluated even if that order changes; such a chain stays a hard break that runs
neither branch. Valid chains fold exactly as upstream, and 0011 changes no class
layout. `scripts/tests/test_xxmi_conditional_fold.py` compiles the verbatim
v1.2.3 optimiser region with boundary stubs and shows that unpatched batching
folds and evaluates an invalid `if` or `elif`, that the real optimiser order
removes it first, and that with 0011 it is never folded or evaluated.

Compatibility package `2.4.3-macgacha.2` adds
`0009-srmi-cursor-coordinate-contract.patch` and
`0010-srmi-invalid-conditional-fail-closed.patch`. It is included in `v0.1.3-xxmi.3`. The standard pinned
`xxmi-rebuild-payload.py` plan now applies both corrections in stage 3 and
rebuilds every first-party translation unit; old objects are incompatible with
the new internal class layouts. The final DLL SHA-256 is
`79da3363543a1f12f014922ae4dceaed0173db4405028d6f9b8c0dad92396ad8`. Third-party object reuse stays hash-checked.
Do not substitute this DLL into an installed package without regenerating and
validating its package manifest and source/build provenance.

The correction separates screen pixels, client pixels and normalized client
coordinates, preserves valid zero and negative client positions, and checks
Win32 query failures. Query results, including failures, are cached for one
command-list state. Although the legacy window-size heuristic functions remain
textually unchanged, their shared query helper now caches failed/zero-size
queries too; a new state retries. Healthy interior coordinates in windows above
the legacy size thresholds retain their old values. Small windows and exact
zero edges intentionally change.

Offline regression tests are in `scripts/tests/test_xxmi_cursor_contract.py`.
A host-only, reproducible DLL build and matching import/export lists are not
proof of Wine input behavior or of a particular mod symptom being repaired.
The reported slider page changes and cross-mod visual conflicts still need
controlled runtime evidence. Repeated local INI section names are already
namespaced by SRMI and must not be renamed blindly. Mods copied from another
manager may depend on that manager's generated namespaces; do not remove those
guards or rewrite the user's originals automatically.

The conditional correction retains malformed `if`, `elif` and `else if` nodes
so their block boundaries stay balanced. An unparseable or empty condition
runs neither branch. Without the correction, SRMI can discard the invalid
condition while still compiling its body and can attach an `endif` to the
wrong outer condition. Regression tests compile the production control-flow
and INI command-list parser regions with boundary stubs, including actual INI
whitespace trimming for blank conditions. They do not establish a live visual
repair. A missing manager dependency still needs its definitions or clean
original mod configurations; disabling an invalid block does not supply it.

The combined experimental DLL rebuild applies 0010 after 0009 with
`--conditional-patch compat/xxmi/patches/0010-srmi-invalid-conditional-fail-closed.patch`.
Both patches change internal class layouts, requiring all first-party
translation units to be rebuilt. Do not mix old and new objects.

## Source updates

1. Read and authenticate the desired upstream release and source commit outside
   this repository; record the release archive and manifest hashes.
2. Replace `source-pins.json` and the patch files; keep patches in the documented
   order and update their hashes.
3. Apply the patches to a clean source copy, rebuild with the explicit toolchain
   and authenticated object inputs, and require the recorded output hash. That
   validates the pinned input set; it is not a clean-room rebuild claim. Never
   merge an unreviewed upstream tree into the app.
4. Regenerate `build/payload-build-plan.json` with
   `scripts/xxmi-derive-build-plan.py`, which builds all three stages from the
   template plan and records every hash, then verify it with an independent
   `scripts/xxmi-rebuild-payload.py --output-dir` run. The plan is derived
   data; do not hand-edit command arrays.
5. Generate the new package, run the focused tests, and keep the previous
   generated package until the new one verifies. The app-side installer keeps
   user mods, settings and previous versions; this tooling never deletes them.

A failed update must leave the previous package and all user data untouched.

## Fork app maintenance and release gate

Keep MacGacha integration in `App/Model/*ModSupport*`, `XXMIPanel`, and the
optional Launch injection adapter. Compare upstream MacGacha changes before
applying them; preserve these integration points and, once provisioned, this
fork’s own update feed and independent signing key. Run `scripts/test.sh` after
an upstream update.

Clean source checkouts can build the app without generated binary resources.
The three bundled-package app tests and the generated-package integration test
are skipped in that case; synthetic installer/import/launch tests still run.
A distributable build must supply and verify `App/Resources/XXMI` first:
`scripts/package-dmg.sh` refuses to package a missing or invalid payload.

The checked-in `release.yml` is still the legacy fork release path. It takes an
`xxmi-*` package tag as `xxmi_package_tag`, downloads and verifies the generated
`manifest.json` and `hsr-srmi.zip` from that same repository, signs the DMG with
Sparkle, generates a one-item `appcast.xml`, and creates a draft release with
three uploaded assets: `MacGacha-<version>.dmg`, its `.sha256`, and
`appcast.xml`. It does not download a toolchain or rebuild DLLs.

That workflow did not produce `v0.3.0-xxmi.1`. The current public release was
prepared manually and has exactly two app assets, with no appcast or DMG
checksum. The app update feed is disabled (`MacGachaForkUpdatesEnabled` is
false) and the fork has no provisioned update signing key, so updates are manual
downloads from the releases page. Do not describe the two-asset layout as an
implemented automated release policy until `release.yml` is changed to match it.

To activate app updates, provision a fork-owned Sparkle public key in
`project.yml`, the corresponding private key as the GitHub Actions
`SPARKLE_ED_PRIVATE_KEY` secret, and set `MacGachaForkUpdatesEnabled` in
`App/Info.plist` to true. Do not reuse upstream’s signing identity. The existing
release workflow verifies the signed DMG and creates a draft release; publication
is an explicit maintainer action. The current fork has no update signing key or
enabled feed.

## Corresponding-source release asset

`scripts/xxmi-source-release.py` builds a verified source archive from the pinned
clean XXMI Libraries tree, generated SimpleMath input, the authenticated
Overlay SPRITEFONT inputs and compatibility plan; it recompiles the final
tree's `DirectX11.res` and requires the pinned digest.
It includes upstream and patched sources, pins, patches, notices and rebuild
scripts. For `2.4.3-macgacha.3`, the source archive and its `.sha256` sidecar are
uploaded to the separate `xxmi-2.4.3-macgacha.3` compatibility release, together
with the raw `manifest.json` and `hsr-srmi.zip`. They are not attached to the
app release, which keeps exactly its two assets. The fork's own app source for
`v0.3.0-xxmi.1` is that GitHub tag. Compiler toolchains and system SDKs are
separate build inputs and are not redistributed.

When the plan pins third-party source-correspondence archives
(`provenance.thirdPartyObjects.sourceCorrespondence`), pass each with
`--third-party-source PATH`. The tool includes them under
`third-party-source/` and fails closed when a declared archive is missing,
altered or an undeclared one is supplied. For the pending update, pass
`--zzz-source` (the tagged ZZMI v1.5.2 tree) as well, so one archive covers the
shared core, both packages' configuration sources and the rebuilt third-party
objects. The archive README names the app tag from `--version`, so generate the
published archive with the final release version.
